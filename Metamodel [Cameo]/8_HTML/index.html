This model is authored with NoMagic Cameo Systems Modeler using UML notation, then transformed to SpecIF via Cameo XMI file and finally transformed to HTML or DOCX.

Properties

Element Type uml:Model

CASCaRA Metamodel

Design goals

  • Separated syntax and semantics: The metamodel governs the graph pattern independently of the ontology. Any software depends on the metamodel and doesn’t need change, when the ontology evolves over time.
  • Interoperability: A graph pattern is designed which may be represented in RDF, JSON-LD, GQL and OOP alike. Bidirectional transformations between any of those formats shall be possible without data-loss. Admittedly this ‘sweet-spot’ reduces expressivity when compared with any of the listed data formats, but the choice of implementation technologies is maximized. Verification and validation will show that the expressivity of the CASCaRA Graph is sufficient for the purpose.
  • Federated data-spaces: The general use of URIs (or UUIDs with namespace) as identifier like RDF allows linked data to reside in multiple internet servers and still form a valid graph which can be seamlessly traversed and queried.
  • Standard queries: The same queries shall be applicable, no matter where the data came from originally.

CASCaRA Metamodel Diagram

The CASCaRA metamodel is a 'platform independent model' (PIM) in OMG terms and defines both the CADSCaRA types (above the dashed line) and the CASCaRA instances (below the dashed line), forming the CASCaRA Product Information Graph in the application domain. CASCaRA types are owl:Class and CASCaRA instances are owl:NamedIndividual. In the specification and implementation domain, both CASCaRA types and instances are application data which are modeled as UML classes:

  • Entity and anEntity are type and instance used for model elements, such as a requirement, a function or a system component.
  • Relationship and aRelationship are type and instance used for relations between elements, such as a 'component satisfies a requirement'. A Relationship type may define a set of Entity or Relationship types, whose instances are eligible as source or target of aRelationship instance which is thus always directed.
  • Employing enumeratedProperty, every Entity and Relationship can define a set of Property, each of which specifies a datatype and range. For example, a requirement might have two 'native' properties „title“ and „description“ plus two configurable properties such as "Category" with datatype xs:string and a maximum length of 32 and „Priority“ with a single value of the Enumeration ['high', 'medium', 'low']“.
  • A datatype may be any of those known from XML. As described above, some parameters of Property may restrict the value range, such as minimum and/or maximum value of a number, a string length or a set of enumerated values is defined by an Enumeration.
  • anEntity or aRelationship is thus an instance of Entity or Relationship respectively. Each instance usually has a set of aProperty corresponding with the Property of its type.
  • aPackage is an instance of Entity and contains a subgraph of the global CASCaRA Graph. aPackage may have a set of aProperty corresponding with the Property of its type. Finally, aPackage can be nested.

Note

  • "Technical" super-class and sub-class in the UML sense are defined in this metamodel by means of UML:Generalization.
  • "Semantic" super-type and sub-type representing types of real world instances are specified by the UML associations with an end 'specializes'.
  • As usual, the UML classes with white background and italic name are abstract.

Constraints

All constraints must be satisfied in addition to the JSON-LD schemata, XML schemata or RDF shapes.

General

  • IDs are unique

Model Integrity

  • Property.type is owl:DatatypeProperty
  • Property.specializes is a Property
  • Property.datatype is a valid xs: datatype
  • Property.maxLength is >0 and only specified, if datatype is xs:string
  • Property.pattern is a regular expression and only specified, if datatype is xs:string
  • Property.minInclusive is only specified, if datatype is a number
  • Property.maxInclusive is only specified, if datatype is a number
  • Property.minInclusive is smaller or equal Property.maxInclusive
  • Property datatype and range must be a super-set of those defined in the specialized Property (following the restrictions of OWL)
  • Property.defaultValue meets datatype and range
  • Property.composes entries are each pointing to a Property
  • Property.composes chain is a tree (without cyclic dependency)
  • Link.type is owl:ObjectProperty
  • Link.specializes is a Link
  • Link.enumeratedEndpoint entries point to either 1 Enumeration, 1..n Entities or 1..n Relationships
  • Link.defaultValue is a valid Id-string (URI or UUID with namespace)
  • Link.enumeratedEndpoints must be a super-set of those defined in the specialized Link (following the restrictions of OWL)
  • Enumeration.type is owl:Class
  • Enumeration.specializes is an Enumeration
  • Enumeration.enumeratedValue complies with the datatype
  • Entity.type is owl:Class
  • Entity.specializes is an Entity
  • Entity.enumeratedProperty entries are each pointing to a Property
  • Entity.enumeratedTargetLink entries are each pointing to a Link
  • Entity.enumeratedProperty and Entity.enumeratedTargetLink entries are super-sets of those defined in the specialized Entity.
  • Relationship.type is owl:Class
  • Relationship.specializes is a Relationship
  • Relationship.enumeratedProperty entries are each pointing to a Property
  • Relationship.enumeratedSourceLink has exactly one entry pointing to a Link
  • Relationship.enumeratedTargetLink has exactly one entry pointing to a Link
  • Relationship.enumeratedProperty, Relationship.enumeratedSourceLink and Relationship.enumeratedTargetLink entries are super-sets of those defined in the specialized Relationship.
  • aProperty is contained in a parent aPackage, anEntity or aRelationship
  • aProperty.type is a Property
  • aProperty.type is contained in enumeratedProperty list of its parent's type (Entity or Relationship)
  • aProperty minCount and maxCount are met, language-aware in case of xs:string
  • aProperty.value is a multilanguage object in case of xs:string, where the language tag is set if more than 1 language is provided
  • aProperty.value is a simple value (literal) in case the datatype is other than xs:string
  • aProperty.value meets the datatype of its type
  • aProperty.composes entries are aProperty
  • aSourceLink is contained in a parent aRelationship
  • aSourceLink.type is a Link
  • aSourceLink.type is contained in the enumeratedSourceLink list of its parent's type (Relationship)
  • aSourceLink.hasEndpoint (idRef) points to an instance of an entry listed as enumeratedSourceLink of its type (Link).
  • aTargetLink is contained in a parent aPackage, anEntity or aRelationship
  • aTargetLink.type is a Link
  • aTargetLink.type is contained in enumeratedTargetLink list of its parent's type (Entity or Relationship)
  • aTargetLink.hasEndpoint (idRef) points either to an instance of an entry listed as enumeratedTargetLink of its type (Link) or to an enumeratedValue of the listed Enumeration
  • aPackage.type is an Entity
  • aPackage.context defines all namespace prefixes used in its (sub-) graph
  • anEntity.type is an Entity
  • aRelationship.type is a Relationship
  • A specializes chain is a tree (without cyclic dependency)

Limitations

  • Enumerations cannot be contained in a composed Property
  • Links cannot be contained in a composed Property
  • all enumeratedEndpoints of a given Link must be of the same item type (Enumeration, Entity or Relationship)
  • Access Permissions per user role are still missing. Role names and the way how to assign permissions per metamodel item shall be included in the standard, whereas the assignment of users to user roles is left to the implementations.

itemType

Denotes CASCaRA types and instances in terms of this metamodel. It must be made explicit in all representations without native reasoner, such as in object-oriented programming, JSON, JSON-LD and XML. It may be omitted in RDF/OWL, as the top of the type hierarchy shall correspond to the metamodel itemType (see CASCARA Semantic Infrastructure and the itemType can be derived with a standard OWL reasoner.

Details:

  • Here it is modeled as a string, but in fact it is an enumerated value for each of the concrete metamodel items (represented as UML classes), thus either Enumeration, Link, Property, Entity, Relationship, aPackage, aSourceLink, aTargetLink, aProperty, anEntity or aRelationship.

Identifiable

All sub-classes of this class (in UML terms) are identifiable, means they have an identifier, a title (name) and optionally a description.

Details:

  • The class is abstract.
  • All attributes are inherited by its subclasses.
  • All type level items in the upper part of the diagram are commonly released and made available with an URL path including the revision. Hence, multiple revisions of a type set may exist in parallel.
  • All instance level items in the lower part of the diagram may be updated individually with change information modified, revision, priorRevision and creator. The prior revision identifier is memorized to support change history and branching. In case of a merge, there are two prior revisions.

Enumeration

A type defining a set of enumerated values, where each value has an id and either a multi-language title in case of datatype xs:string or otherwise a simple value.

A corresponding Link type must be defined with an enumeratedEndpoint to this Enumeration. For example, anEntity 'Requirement-XYZ' has aTargetLink 'Priority' pointing to aValue 'medium' being an instance of Enumeration 'Priority-Values'.

Details:

  • The set of enumerated values of a specialized Enumeration must be a subset of those of its super-type.
  • Enumeration is modelled as a sub-class of Element, however there is no known use-case where configurable properties (enumeratedProperty) make sense.

Relationship

A type of relationships between two entities to allow assertions such as 'a system component satisfies a requirement'. All relationships are bilateral and directed. This allows for statements according to propositional logic. They can be easily mapped to many technologies such as RDF or even ReqIF. Being reified, a Relationship is an owl:Class.

Details:

  • Relationship must have a title (name) and may have a description (definition).
  • Relationship lists zero to many property types its instances may have.
  • Relationship may define (configure) entitiy types or relationship types, whose instances are eligible as source resp. target in a relationship. If none are defined, all entities and relationships are eligible.
  • Relationship is reified (as a rdfs:Resource in RDF), so that it can be a source or target of another Relationship - to make a statement on a statement.
  • The definitions of a relationship together with those of their properties may be used to build user dialogs with input verfication and to check its instances whether all properties have a correct type and value range as well as whether all required ones are present.

Configurable

Besides 'native' properties which are defined by the metamodel (such as title and description), an Element can have configurable properties and links. Those configurable properties and links support a dynamic data model, so that the ontology can evolve over time without software change. Additional detail such as data type and range can be provided to build dynamic forms, for example. It is in fact the core feature to separate CASCaRA syntax and semantics.

Details:

  • This class is abstract.

Property

Every type Entity and Relationship can have an individual set of configurable properties, each of which is uniquely defined by id (name), datatype and range. A Property is an owl:DatatypeProperty.

Details:

  • Property type must have a title and may have a description.
  • Property type may define a minimum and maximum count of values.
  • Property type must define a datatype and may restrict its range by minInclusive, maxInclusive or or a pattern defined by Regular Expression.
  • A property type may define a default value which must of course satisfy its own data type and range.
  • Property type may be composed of multiple property types to form a structured data type (xs:complexType). The structure must be a tree, thus without cyclic dependency.

Example:

  • A requirement might have a configurable property, such as 'Category' with datatype xs:string with a maximum length of 32.
  • A Priority with a single choice of values ['high', 'medium', 'low']“ would be defined as a Link to an Enumeration.

Link

Is an identifiable link type. It is used as a named connector between a reified Relationship and its source and target, or as a named connector between an Entity and a directly related target. A Link is an owl:ObjectProperty.

Details:

  • A link type can be specialized by another. For example the most global 'linksTarget' may be specialized by 'depicts'.
  • If revisionAware is set for a Link, each endpoint of its instances is deleted as soon as the referenced endpoint itself is updated.

Examples:

  • An Organizer (semantic sub-type of Entity) may list Requirements (another semantic sub-type of Entity) to construct a document outline. As such the Link type lists is specified as enumeratedTargetLink by Organizer.
  • An Entity Requirement might have a property with enumerated values ['high', 'medium' or 'low']. This is represented by a Link type pointing to an Enumeration defining those values.

revisionAware

Indicates whether an instance of this type is valid for a specific or any revision of the specified endpoints.

Details:

  • If revisionAware is set, all references occurring as endpoint of its instances are deleted as soon as the endpoint itself is updated; otherwise they are preserved.
  • In rare cases only one of a Relationship's enumeratedSourceLink or enumeratedTargetLink can be 'revisionAware'.

Examples:

  • aLink named lists of an outline (folder) shall continue to reference an endpoint, even if updated. So revisionAware of its Link type is omitted or set to 'false'.
  • aRelationship named verifies shall apply between specific revisions of a test-case and a requirement. So the types of both aSourceLink and aTargetLink set revisionAware to 'true'. If the requirement is updated, it has no more verifies relationship, until explicitly set after repeating the test-case.

CASCaRA Semantic Infrastructure

The CASCaRA Semantic Infrastructure complements the CASCaRA Metamodel by further sub-typing its items in the application domain. The idea is to keep the metamodel as simple as possible and add semantic precision through the semantic infrastructure.

Let's consider the paradigm of separating syntax and semantics with the objective to shield the software from an ontology under evolution over time. In all likelihood, the CASCaRA Semantic Infrastructure will be used by software for reasons of simplicity. Therefore it is advised to treat the semantic infrastructure similarly to the metamodel: Change it seldomly and keep it downward compatible. Thus, software built assuming an older version shall not break when a new version of the metamodel or semantic infrastructure is adopted. So the semantic infrastructure can be seen as an intermediary layer between metamodel and ontology.

Thus, an ontology for use with the CASCaRA Metamodel SHOULD sub-type the items of the CASCaRA Semantic Infrastructure.

Property

Every type Entity and Relationship can have an individual set of configurable properties, each of which is uniquely defined by id (name), datatype and range. A Property is an owl:DatatypeProperty.

Details:

  • Property type must have a title and may have a description.
  • Property type may define a minimum and maximum count of values.
  • Property type must define a datatype and may restrict its range by minInclusive, maxInclusive or or a pattern defined by Regular Expression.
  • A property type may define a default value which must of course satisfy its own data type and range.
  • Property type may be composed of multiple property types to form a structured data type (xs:complexType). The structure must be a tree, thus without cyclic dependency.

Example:

  • A requirement might have a configurable property, such as 'Category' with datatype xs:string with a maximum length of 32.
  • A Priority with a single choice of values ['high', 'medium', 'low']“ would be defined as a Link to an Enumeration.

Relationship

A type of relationships between two entities to allow assertions such as 'a system component satisfies a requirement'. All relationships are bilateral and directed. This allows for statements according to propositional logic. They can be easily mapped to many technologies such as RDF or even ReqIF. Being reified, a Relationship is an owl:Class.

Details:

  • Relationship must have a title (name) and may have a description (definition).
  • Relationship lists zero to many property types its instances may have.
  • Relationship may define (configure) entitiy types or relationship types, whose instances are eligible as source resp. target in a relationship. If none are defined, all entities and relationships are eligible.
  • Relationship is reified (as a rdfs:Resource in RDF), so that it can be a source or target of another Relationship - to make a statement on a statement.
  • The definitions of a relationship together with those of their properties may be used to build user dialogs with input verfication and to check its instances whether all properties have a correct type and value range as well as whether all required ones are present.

revisionAware

Indicates whether an instance of this type is valid for a specific or any revision of the specified endpoints.

Details:

  • If revisionAware is set, all references occurring as endpoint of its instances are deleted as soon as the endpoint itself is updated; otherwise they are preserved.
  • In rare cases only one of a Relationship's enumeratedSourceLink or enumeratedTargetLink can be 'revisionAware'.

Examples:

  • aLink named lists of an outline (folder) shall continue to reference an endpoint, even if updated. So revisionAware of its Link type is omitted or set to 'false'.
  • aRelationship named verifies shall apply between specific revisions of a test-case and a requirement. So the types of both aSourceLink and aTargetLink set revisionAware to 'true'. If the requirement is updated, it has no more verifies relationship, until explicitly set after repeating the test-case.

title

A multiLanguageText. Maps to dcterms:title or rdf:label.

Details:

  • Here a multiplicity [0..1] is given, but in fact that depends on the itemType.
  • For all types (Enumeration, Property, Link, Entity and Relationship), a title is mandatory.
  • In case of anEntity at least one of title or description is required, because it must be possible to represent a text paragraph as anEntity, which simply does not have a title.
  • In case of aRelationship both title and description are optional. If missing, the title and/or description of the respective Relationship type applies. This avoids lots of repetition in real-world data-sets.
  • The same applies for aProperty, aSourceLink and aTargetLink; both title and description are optional and the respective properties of the type apply.
